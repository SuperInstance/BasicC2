## Friction log (running)

### F1 — MAJOR — README.md describes a different product
The repo-root README.md (the file GitHub shows and the file every
new operator reads first) is the *upstream* BasicC2 README. It tells
me to edit a shared secret into `control_server.py`, run
`target_server.py` "slaves", and type commands broadcast to all of
them. It never mentions `fleet/`, `README-OPS.md`, or `DESIGN.md`.
DESIGN.md explains the upstream files are "kept untouched for
provenance", which is fine as history — but there is zero signpost
from README.md to the actual current system. A cold user following
the front page would set up the old, insecure broadcast-shell tool
and never learn the fleet system exists.
Failed me at: README.md (whole file); missing pointer in README.md
to README-OPS.md.

### F2 — MINOR — DESIGN.md assumes insider context
DESIGN.md ("What this is") says the system is "for Casey's own
agent fleet" and the topology section explains the controller "runs
on the LAN hub" because "Oracle public inbound is blocked". As an
outside reader I can infer enough to proceed, but the design record
is written for the household, not for a new operator. Not a blocker;
README-OPS.md is self-contained enough.
Failed me at: DESIGN.md §"What this is", §"Topology".

### F3 — MINOR — enrolling for localhost is a guess
README-OPS §2 enroll example uses `--host <controller-LAN-address>`.
For a same-machine playtest I guessed `--host 127.0.0.1` (the host
presumably lands in the agent's config as where to dial the
controller). No doc states what the enroll --host means or that
127.0.0.1 is a valid choice for local use.
Failed me at: README-OPS.md §2.

### F4 — MINOR — controller lifecycle is unspecified
README-OPS §1 shows the controller as a foreground "# long-running"
command. No guidance on backgrounding it, where its output goes, or
how to stop it later. I used nohup + a log file of my own invention.
Failed me at: README-OPS.md §1.

### F5 — MAJOR — no documented way to SEE a job's output
The census worked, but the actual answers (hostname, uptime, df
tables) are not shown by any documented command. `desk jobs` shows
status only; `desk derive` shows only MINTED verdicts. The results
live inside `ops-state/jobs/<job_id>.json` under "results" — the
README-OPS state table describes that file as "per-job status",
which badly undersells it. I found the data by guessing the state
files were the place to look. For the system's headline use case
(run things on boxes, read what came back) the read path is
undocumented.
Failed me at: README-OPS.md §3, §4, state-layout table.

### F6 — MINOR — `desk jobs` can't tell my census jobs apart
Eight jobs, four of them "kind=run" per agent — the jobs listing
shows target/kind/status but not argv. Which run was `hostname`
and which was `df`? Only my shell history and the job files know.
A census operator has to correlate job ids by hand.
Failed me at: README-OPS.md §3 (jobs description).

### F7 — MINOR — stdout is a truncated preview, full output unrecoverable
`df -h` output in the result is cut mid-line ("…13% /home/ha").
DESIGN.md says the result carries `stdout_preview` + `stdout_sha256`,
so a careful DESIGN reader knows it's a preview — but neither doc
states the preview size, and there is no way to retrieve the full
output afterwards. The sha256 proves what the full output was
without letting you read it.
Failed me at: DESIGN.md §"The two-mint job model"; README-OPS.md
(never mentions previews at all).

## Experiments (mission step 5 — beyond the docs)

### E1 — Non-allowlisted command (03:24:49)
`send --target alpha --kind run -- cat /etc/passwd` (cat is not in
alpha's allowlist). Result: job shows `status=refused refused by:
alpha` in `desk jobs`; the job file records the reason
("refused": {"alpha": "not_allowlisted"}). Derive gives
NOT-MINTED (task: missing_mirror, result: no_send), verdict
NOT COMPLETE, exit 1 — the refusal semantics are exactly as
DESIGN.md describes: the agent booked nothing, so there is nothing
to agree with. The controller ledger grew by one entry (its own
SEND booking), which is consistent with the design.
Surprise, small: neither the agent log nor the controller log
mentions the refusal — both logs contain only their startup lines
for the entire session. All diagnostics live in the state files.
No doc covers logging at all (see F9).

### E2 — Job to a stopped agent, then agent returns (03:25:11)
Killed beta. Within ~3 s `desk agents` showed beta offline
(online.json is prompt and accurate while the controller lives).
Sent ping to beta: job sat at `status=queued`. Restarted beta:
the queued job was dispatched on reconnect, completed, and
derives COMPLETE (both exchanges MINTED). DESIGN.md only warns
the job "stays queued forever" if the target *never* connects —
the drain-on-reconnect behaviour is real but undocumented;
a pleasant surprise, recorded here because a user would
otherwise assume queued-while-down means lost.

### E3 — Controller killed and restarted mid-flight (03:25:41)
Killed the controller. Two observations:
1. `desk agents` kept reporting both agents ONLINE from the stale
   online.json — nothing in the output warns that the file is
   only as fresh as the last controller heartbeat, and the
   controller was dead. The only tell is the old "since"
   timestamps. This is the controller-side mirror of DESIGN.md's
   own "zombie registration" finding, and it's the most
   operationally dangerous thing I found: during an outage the
   desk confidently lies about fleet state. (See F10.)
2. `desk send` during the outage worked fine — the job queued in
   the inbox (the file channel needs no live controller, as
   DESIGN.md says).
Restarted the controller: both agents reconnected within ~10 s
(new source ports, fresh "since" times), the outage-queued job
dispatched, completed, and derives COMPLETE. A pre-restart census
job also still derives COMPLETE — records survive process death,
which is the core promise, kept.

### F9 — MINOR — logging is a black box
Controller and agent logs contained exactly one startup line each
for the whole session — enrollments, dispatches, refusals,
disconnects, reconnects: none of it logged anywhere I could find.
Every diagnostic question I had was answered by state files or not
at all. No doc mentions logs or troubleshooting.
Failed me at: no doc covers this (README-OPS.md, DESIGN.md silent).

### F10 — MAJOR — `desk agents` lies when the controller is dead
With the controller process killed, `desk agents` reported both
agents ONLINE, reading a stale online.json with no staleness
indication. An operator checking the fleet during a controller
outage gets confident, wrong output — and README-OPS §3 says jobs
status comes "from the state files — no need to ask the controller
process anything", which trains exactly the trust this breaks.
The same caveat presumably applies to `desk jobs` statuses during
an outage (they'd freeze at last-written values).
Failed me at: README-OPS.md §3; online.json semantics in the
state-layout table (says "who's connected right now" — it is
actually "who was connected when the controller last wrote").

## Verdict — useful, with a misleading front door

Useful, not theatre. The core loop does the thing it claims, at
the speed it claims, and the receipt model survived everything I
threw at it: the proof of a job is two signed records agreeing,
and that proof kept working after I killed every process
involved. The refusal path is as well-behaved as the success path,
which is rare and is the actual product.

But a cold user has roughly one chance in three of ever reaching
that core: the front README teaches a different, worse tool; the
ops guide never tells you how to read the answers your jobs bring
back; and the one status display an operator would trust during
an outage is the one that lies then. The engine is real. The
instrument panel and the front door are not finished. Fix F1 and
F5 and this goes from "impressive to its builders" to "usable by
the next operator" — which, for a system whose entire pitch is
*don't take the process's word for it*, is the gap that matters.
